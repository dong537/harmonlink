# 专线平台全流程

本文档梳理 365 专线代理平台的完整业务流程、数据模型与平台契约，并标注每个环节的实现状态。

结论摘要：**仍不具备生产条件，但阻断项已从「代码缺陷」变为「缺配置」**。原先会导致「扣款但不交付、且预留不释放」的主链路缺陷 [P0-1](#p0-1-下单链路字段契约断裂已修复2026-08-23-核实) 已修复并核实（`38/38` spec 通过，`tsc --noEmit` 干净）。当前剩余阻断项：生产库五层价格全空（[P0-2](#p0-2-生产库五层价格全空专线无法下单)，需产品定价）、API key `scopes` 从不校验、`OPERATOR` 被静默提升为 `PLATFORM_ADMIN`。此外有 3 处权限缺陷、5 处多站隔离缺陷。

所有 `路径:行号` 均指向 `apps/api/src` 或 `packages/`。**`apps/api/dist/` 是陈旧编译产物**（含 `src/` 已删除的 `modules/dedicated/`），阅读时应忽略。

## 1. 系统构成

pnpm monorepo，三个应用 + 五个包。

| 应用 | 职责 | 模块数 |
|---|---|---|
| `apps/api` | NestJS + Prisma，HTTP 接口与业务用例 | 34 |
| `apps/web` | React + Ant Design + TanStack Query + react-i18next | — |
| `apps/worker` | 六个轮询 worker，异步执行采购与投影下发 | 6 |

包：`packages/db`（Prisma schema + 迁移）、`packages/contracts`（OpenAPI 生成的类型）、`packages/config`、`packages/tsconfig`、`packages/eslint-config`。

两套订单栈并存，互不相通：

- **静态代理（旧）** — `orders` 表，按 `resourceId` 计价，`fulfillment_jobs` 履约
- **专线（当前）** — `dedicated_line_orders` 表，按 `skuId` 计价，`external_jobs` 履约

两者没有共同抽象，「列出某用户全部订单」无法用单条查询完成。

### 阶段三：选节点与落点策略

`create-placement-policy.use-case.ts`（仅运营）校验并落库策略：

- 节点组与 inbound profile 都必须 ACTIVE，否则 404 `placement_reference_not_found`（`:28`）
- `inboundProfile.nodeGroupId` 必须等于策略的组，否则 422 `placement_inbound_group_mismatch`（`:46`）
- `minReadyReplicaCount ≤ targetReplicaCount`（`:20`）
- `allowedNodeIds` 每一项都必须解析为该组内、租户可见的 ACTIVE 节点；部分匹配即 422 `placement_allowed_node_invalid`（`:52`）
- `allowedNodeIds.length < targetReplicaCount` → 422 `placement_allowed_nodes_insufficient`（`:55`）

策略通过三个层次限制落点：`allowedNodes` 关联表是硬白名单，`nodeGroupId` 划定范围，`inboundProfile.controlNodeId`（可空）能把线路钉到唯一节点。

落库时的实际选择在 `dedicated-line-order.repository.ts:405` `allocateProjectionNodes`：按 `siteId` + `nodeGroupId` + `id IN allowedNodeIds` + `status='ACTIVE'` + 租户可见性过滤（`:409`），余量算作 `min(capacityUnits, maxUnitsPerNode) - allocatedUnits`（`:420`），按余量最多、再按 `code` 选出 `targetReplicaCount` 个，然后用带 `allocatedUnits < capacityUnits AND allocatedUnits < maxUnitsPerNode` 守卫的条件 UPDATE 递增（`:437`）。不足即 422 `CONTROL_NODE_CAPACITY_EXHAUSTED`。

> **`control_nodes.regionCode` 从不参与选节点。** 它在建节点时写入（`dedicated-line-control-plane.admin.controller.ts:78`）、在列表里回显（`:36`、`:158`），但下单、落点、投影、健康、迁移全链路没有任何查询按它过滤或打分。订单里的 `regionCode` 只是**上游采购提示**，流向快照和 `buyStaticProxy` 调用（`process-dedicated-line-order.use-case.ts:77`），不影响节点选择。
>
> 这一点直接关系到「开一条美国线路」：地域目前由**上游采购参数**决定，不由控制节点位置决定。

`CONTROL_NODE_CAPACITY_EXHAUSTED` 与 `DEDICATED_LINE_CONFIG_INVALID` 在 `:291` 被捕获并转入 `persistPurchasedExitsForOperator`（`:456`）：已采购的出口存为未分配的 `residential_exits`，预留标记 CONSUMED，任务转 `NEEDS_OPERATOR`。钱没有静默丢失，但线路也没有建成——**需要有人真正处理这个运营队列**。

租约过期的处理是刻意保守的：`recoverExpiredLeases`（`:82`）把订单任务直接送去 `NEEDS_OPERATOR` 并标 `remote_order_may_have_been_accepted`，而不是重试，因为采购可能已在上游落地。

### 投影（projection）是什么

一条投影 = **每个（线路 × 控制节点）组合的期望状态记录**，落在 `dedicated_line_projections` 表，`projectionKey` = `${lineId}:${nodeId}`（`dedicated-line-order.repository.ts:235`）。

**API 是权威源，控制节点向它收敛。** 每条投影携带 `desiredVersion` + `desiredHash`（规范化请求 JSON 的 SHA-256，`dedicated-line-projections/domain.ts:4`），并记录从节点读回的 `observedVersion` / `observedHash`。

传输方式是**对控制节点面板 API 的 HTTPS JSON 调用**，不是 gRPC 也不是消息总线（`managed-line-projection.adapter.ts:119`）：

```
{baseUrl}/panel/api/managed-line-projections/{projectionKey}
```

`PUT` upsert、`GET` 读取、`DELETE`（带 `?desiredVersion=`）拆除（`:65-105`）。鉴权用 `apiCredentialCiphertext` 以 `APP_ENCRYPTION_KEY` 解密后的 `Bearer`（`:117`、`:149`）。baseUrl 过 `assertSafeUrl` SSRF 守卫（`:116`）。

下发的载荷（`build-managed-line-projection-request.ts:23`）：`desiredVersion`、`inboundTag`、`protocol`、`client`（VLESS/VMESS 用 email + `id`，MIXED 用 `user`/`password`）、`egress`（上游住宅代理的 host/port/账号/密码，在此解密）、`lifecycle`（`enabled`、`expiresAtMs`、`trafficLimitBytes`、`ipLimit`、上下行限速、最大连接数）。

远端状态映射（`:183`）：404 → `managed_line_projection_not_found`，409 → conflict，401/403 → 502 `UPSTREAM_DISABLED`，408/429 → 504 `UPSTREAM_TIMEOUT`，400/422 → 422，其余 502。

`ProcessDedicatedLineProjectionUseCase`（`process-dedicated-line-projection.use-case.ts:24`）从数据库重建请求，并且：

- **重算哈希 ≠ 存储的 `desiredHash` 就拒绝下发**（409 `managed_line_projection_desired_hash_mismatch`，`:32`）
- 要求严格读回一致：同 key、`observedVersion === desiredVersion`、`status === 'ACTIVE'`、`desiredHash === observedHash`，否则 502 `managed_line_projection_readback_mismatch`（`:39`）
- 只有 `UPSTREAM_TIMEOUT` / `UPSTREAM_ERROR` 会重试，其余直接 `NEEDS_OPERATOR`（`:59`）

下发前置检查（`:68`）：节点 DISABLED、inbound 未激活、inbound 被钉到别的节点、出口状态不符（应为 `ASSIGNED`，迁移中允许 `RESERVED`）、出口过期、线路过期。

### inbound_profiles 的作用

`inbound_profiles`（`packages/db/prisma/schema.prisma:1211`）是线路复用的**共享服务端监听器**，提供 `protocol`、`inboundTag`、`listenPort`、可选 `transportConfig`、可选 `controlNodeId` 钉定。

它是落点策略（`line_placement_policies.inboundProfileId`）与线路（`dedicated_lines.inboundProfileId`）的连接点，`inboundTag` 告诉节点把新客户端挂到哪个已存在的 inbound 上。`@@unique([siteId, controlNodeId, inboundTag])` 防止同节点 tag 冲突。

四处闸门引用它：策略创建（`create-placement-policy.use-case.ts:46`）、落点解析（`dedicated-line-placement.repository.ts:56`）、投影前置检查（`process-dedicated-line-projection.use-case.ts:70`）、路由导入（`delivery-route-import.use-case.ts:82`，此处 `listenPort` 必须与导入的路由完全一致）。

### 就绪度汇总

`updateLineReadiness`（`dedicated-line-projection.repository.ts:325`）统计当前 `desiredVersion` 下 `status='READY'` 且 `observedVersion === desiredVersion` 的投影数：

| 条件 | 线路状态 |
|---|---|
| ready ≥ minReady **且当前无交付路由** | `MIGRATING_AWAITING_ROUTE_IMPORT` |
| ready ≥ target | `ACTIVE` |
| ready ≥ minReady | `DEGRADED` |
| 其他 | `PROVISIONING` |
| 终态失败 | `DEGRADED` / `FAILED` |

**线路在运营导入交付路由之前不可用。** 导入接口 `POST /admin/delivery-routes/import`（`delivery-routes.controller.ts:17`）通过 `settleLineStatus`（`delivery-route-import.use-case.ts:219`）将其翻转为 ACTIVE/DEGRADED。

### 客户读取

`GET /dedicated-lines` / `GET /dedicated-lines/:id` → `dedicated-line-delivery.use-case.ts:13`。客户端凭据**仅在 ACTIVE 或 DEGRADED 状态下解密**，否则 `client: null`（`:35`、`:55`）；身份密文损坏 → 500 `dedicated_line_client_identity_invalid`（`:60`）。

注意 `:16` 与 `:26` 用 `tenantId: ctx.tenantId ?? ''` 作用域化，所以空租户上下文会静默匹配不到任何行，而不是报错。

### 阶段五：交付后的生命周期

所有变更都遵循同一个**升版本再重投影**模式：重算请求 → 求哈希 → `desiredVersion + 1` → 把所有投影重置为 `PENDING` 并清空 observed 字段 → 按节点各入队一个 `APPLY_DEDICATED_LINE_PROJECTION` 任务，key 为 `projection:{lineId}:{nodeId}:v{version}`。

**续费** — `dedicated-lines/renew-dedicated-line.use-case.ts:23`。按钱包币种重新报价（`:33`），`Serializable` 事务（`:132`），账本 key 幂等重放（`:56`），要求出口为 `ASSIGNED` 且有 ACTIVE 分配（`:62`），并且**拒绝把线路延长超过其上游出口的到期时间** → 422 `dedicated_line_exit_expiry_insufficient`（`:68`）。

**限额** — `update-dedicated-line-limits.use-case.ts:35`。仅 `PLATFORM_ADMIN` 或 `TENANT_ADMIN`（`:36`，403 `admin_only`），租户管理员自动限定到本租户（`:44`）。要求可变状态（`:67`）、至少一条投影（`:70`）、有效分配（`:73`）、**`reason` 必填**（`:187`），限额未变则短路（`:79`），审计日志记录前后值（`:145`）。

**暂停/恢复** — `dedicated-line-lifecycle.use-case.ts:18`。`POST /dedicated-lines/:id/{suspend,resume}`，用户作用域。已在目标状态时幂等（`:35`），由显式状态机 `assertDedicatedLineTransition` 守卫（`:36`），恢复时重新校验线路与出口两个到期时间（`:120`）。

**域名绑定** — `line-domain-bindings.use-case.ts:13`，仅运营，经 `PUT /admin/control-plane/lines/:id/domains`。幂等表重放（`:23`），替换即退役语义（`:45`），形状严格：恰好一个 `PRIMARY`、至少一个 `BACKUP`、≤32 条、host:port 不重复（`:80`）。

> 域名变更**不**升 `desiredVersion` —— 域名属于路由层，不属于投影层。

**健康** — `dedicated-line-health/control-node-health.use-case.ts:10`，由 worker 循环驱动（`apps/worker/src/main.ts:94`），非 HTTP。对每条投影发 `GET`，写一行 `control_node_health_observations`，成功则打 `lastHealthyAt`；遇 `PROJECTION_DRIFT` 或 `CONTROL_NODE_UNREACHABLE` 则开一条去重的 `dedicated_line_migration_recommendations`，按容量对候选节点排序（`:46`）。经 `GET /admin/control-plane/lines/recommendations` 读取。

**迁移** — `modules/dedicated-line-migrations/`，分阶段推进：

```
PREPARE → CANARY_ROUTE → VERIFY → CUTOVER_ROUTE → COMMIT → CLEANUP
```

带 smoke 测试闸门（`migration-smoke.adapter.ts`）与 `DELETE_DEDICATED_LINE_PROJECTION` 拆除任务。**两种形态被显式拒绝为未实现**：`EXIT_ONLY` 迁移 → 422 `migration_exit_only_staging_unsupported`（`create-migration.use-case.ts:45`）；任何跨迁移保留节点的情形 → 422 `migration_retained_node_staging_unsupported`（`:48`）。所以只有整组节点替换可用。

跨模块安全：已排定删除时，在途的 apply 任务会被置为失败而非被应用（`dedicated-line-projection.repository.ts:69`）。

## 3. 阻断性缺陷

### P0-1 下单链路字段契约断裂（已修复，2026-08-23 核实）

**原缺陷。** 同一个 `request` 对象，生产者只写 6 个字段，消费者 `parseRequest` 强制要求 13 个。缺 `protocol`、`currency`、`placementPolicyId`、`inboundProfileId`、`inboundTag`、`lineProtocol`、`maxReplicaFanout`。

`parseRequest` 是 `execute` 里 `try` 块的第一行，在任何上游调用之前，所以每一笔专线订单被 worker 取到就抛 `VALIDATION_ERROR`。而当时的 catch 块按错误码白名单判断是否释放预留：

```ts
const isKnownNoPurchaseFailure = code === ErrorCode.UPSTREAM_OUT_OF_STOCK
  || code === ErrorCode.UPSTREAM_DISABLED;
```

`VALIDATION_ERROR` 不在名单里，于是 `retry: false, releaseReservation: false`。后果是**钱包已扣（`DEBIT` 已落 `ledger_entries`）、库存已占、预留不释放、任务不重试、线路不存在**，每笔订单都命中，只能人工介入。

**当前状态：两侧都已修复，`38/38` spec 通过，`tsc --noEmit` 干净。**

字段侧 —— `CreateDedicatedLineOrderUseCase` 现在注入 `DedicatedLinePlacementRepository`（`create-dedicated-line-order.use-case.ts:43`），并在**任何资金动作之前**解析落点（`:85-91`），`jobPayload`（`:120-131`）补齐了全部缺失字段：`protocol`、`currency`、`placementPolicyId`、`inboundProfileId`、`inboundTag`、`lineProtocol`、`maxReplicaFanout`。`:82-84` 的注释写明了意图：落点在资金动作前解析，策略缺失或不可满足就以 422 结束请求，而不是把已付款的预留搁死在 worker 里。

`providerResourceId` 不由生产者提供，而由 inventory repository 在入队时注入（`dedicated-line-inventory.repository.ts:286`）。这个分工在类型层面被固定下来（`domain.ts:28`）：

```ts
export type DedicatedLineOrderRequestDraft = Omit<DedicatedLineOrderRequest, 'providerResourceId'>;
```

于是「生产者该写哪些字段」不再是三个文件间的口头约定，字段缺失在编译期就被挡住。

分类侧 —— 白名单被删除，换成按流程位置判断（`process-dedicated-line-order.use-case.ts:138`）：

```ts
const releaseReservation = !upstreamCallIssued;
```

`upstreamCallIssued` 在真正调用上游的前一行才置 true（`:78`）。`:131-137` 的注释点明了原来的病根：按错误码枚举「安全」失败，等于把任何**新增**的购买前失败默认当成购买后失败。改成按位置判断之后，以后新加的前置校验会自动被正确归类，不需要维护名单。

这个修法比「把 `VALIDATION_ERROR` 加进白名单」更彻底：白名单只修已知的一个码，位置判断修的是整类问题。

**遗留：契约测试缺口仍然存在。** 当初两侧 spec 都绿是因为 `process-…spec.ts` 自己构造完整的 13 字段 payload，而 `create-…spec.ts` 只断言返回值和 repository 调用参数 —— **没有任何测试让真实生产者的输出流进真实消费者的解析器**。字段现在靠 `Omit` 类型保护，但 `parseRequest` 读的是运行时 JSON，类型不覆盖「repository 展开 payload 时字段名写错」这类问题。建议补一个跨两侧的测试：真实调用 create 用例 → 读回 `external_jobs.payload` → 交给真实 `parseRequest`。

**遗留：排序器不一致。** `resolveForOrder` 的容量比较器按**利用率**排序（`dedicated-line-placement.repository.ts:80-84`），而落库时 `allocateProjectionNodes` 按**余量最多**排序（`dedicated-line-order.repository.ts:420-423`）。两者应统一，否则同步阶段试算出的节点与实际落点可能不是同一个。


### P0-2 生产库五层价格全空：专线无法下单

生产数据库五层价格全部为空：`rules=0 overrides=0 userOverrides=0 templates=0`。

SKU `SV` 与 `ZB` 都是 `capabilities.delivery = 'dedicated-line'`、`isActive`、`isVisible`，但无任何价格候选 → `SkuQuoteUseCase` 抛 `PRICE_MISSING` / `no_sku_price_rule` 422。下单在阶段二就终止，走不到 P0-1。

这是**缺配置，不是代码缺陷**，而且恰好证明报价链正确地 fail closed 而非凭空造价。需要产品先定：币种、时长档位、单价、最小起订量、以及配在哪一层（站点默认模板还是租户默认模板）。

### P0-3 缺全局 ValidationPipe

`class-validator` **既未被使用也不在依赖里**，DTO 只是编译期 TypeScript 类型，运行时没有任何校验。实测：

| 请求 | 实际 | 应为 |
|---|---|---|
| `POST /api/auth/login {}` | **500** | 400 |
| `POST /api/auth/login {email:123,password:null}` | **500** | 400 |
| `POST /api/auth/login`（无 body） | 400（Fastify 层拦下） | 400 |
| `POST /api/auth/register {}` | 400（手写检查） | 400 |

专线链路因为把校验全部手写在用例里（`create-dedicated-line-order.use-case.ts:136-148`），受影响较小；但这是全 api 范围的问题——任何依赖 DTO 类型而没手写校验的 handler 都会把类型错误暴露成 500。

修它会改变全 api 的错误契约（大量 500 变 400），属于新增范围，**待确认后再动**。

## 4. 权限缺陷

### P1-1 管理控制面把授权放在用例体内

`dedicated-line-control-plane.admin.controller.ts:20-21` 只在类级挂 `@Controller('admin/control-plane')` + `@RequireAuth()`。`@RequireAuth()` 只验证「已认证」，不验证「是运营方」。真正的授权靠每个 handler 自己调 `requireOperatorContext(ctx)`。

四个 handler 在控制器层没有调用它：

| 行号 | 路由 | 控制器层 | 内层是否补上 |
|---|---|---|---|
| `:120` | `POST placement-policies` | ❌ | ✅ `create-placement-policy.use-case.ts:10` |
| `:135` | `PUT lines/:id/domains` | ❌ | ✅ `line-domain-bindings.use-case.ts:14` |
| `:140` | `PUT lines/:id/limits` | ❌ | ⚠️ 换了一套判定（见下） |
| `:150` | `GET lines` | ❌ | ⚠️ 同 `limits` 的另一套判定（`list-line-limits.use-case.ts:11`） |

今天不构成越权，因为内层各自检查了。但这个结构的问题是：**授权正确性依赖每个新 handler 的作者记得手写一行**。漏一次，就是对任何登录用户开放的管理接口。守卫存在的意义正是让这件事不靠记性。

正确做法是把 operator 检查提到守卫层（类级 `@RequireOperator()` 之类），让「忘记写」变成默认拒绝而不是默认放行。

### P1-2 `PUT lines/:id/limits` 使用与其他管理接口不同的授权语义

`update-dedicated-line-limits.use-case.ts:36` 不用 `requireOperatorContext`，而是：

```ts
if (ctx.ownerType !== 'PLATFORM_ADMIN' && ctx.ownerType !== 'TENANT_ADMIN') { ... }
```

并在 `:44` 按 `TENANT_ADMIN` 追加 `tenantId` 过滤。这是一个**有意的**能力扩展（让租户管理员改自己租户线路的限额），设计上说得通。问题在于它与 `requireOperatorContext` 并存却没有共同抽象：同一个控制器下，两个路由的「管理员」含义不同，且差异只能靠读用例源码发现。

租户边界本身是收敛的（`TENANT_ADMIN` 被 `tenantId` 夹住）。这里的风险是可维护性，不是当前越权。

### P1-3 `SYSTEM` 主体与人类管理员共用同一入口

`requireOperatorContext` 同时接纳 `PLATFORM_ADMIN` 和 `SYSTEM`（审计写入处按 `ctx.ownerType === 'SYSTEM' ? 'SYSTEM' : 'ADMIN_USER'` 区分，见 `create-placement-policy.use-case.ts:80`、`line-domain-bindings.use-case.ts:54`）。机器主体与人类主体拿到完全相同的控制面权限。审计能区分二者，授权不能。

补充一点：`ownerType: 'SYSTEM'` **实际不可达**——没有任何认证策略会产出它（`jwt.strategy.ts` 只产出 `USER`/`TENANT_ADMIN`/`PLATFORM_ADMIN`，`apikey.strategy.ts` 产出 key 上记录的 ownerType）。所以 `RequireSystem()` 守卫的路由是死路由，而 `requireOperatorContext` 里的 `SYSTEM` 分支today 也走不到。这是「预留了机器主体但没有签发路径」的状态。

### P1-4 API key 的 scopes 从不校验（全局，非专线专有）

`api_keys.scopes` 被持久化、并由 `apikey.strategy.ts:35` 注入 `AuthenticatedContext.scopes`——这是全仓库唯一填充 `scopes` 的路径（`jwt.strategy.ts:44` 恒设 `scopes: []`）。

但 `apps/api/src` 里 `scopes.includes` / `hasScope` / `requireScope` **零命中**。所有守卫只判 `ownerType`。

后果：**任何 ACTIVE 的 API key 权限等于其 `ownerType` 的全量能力**。一个本应只读库存的 key 和一个能下单扣款的 key 没有任何区别。scopes 字段给出了「已做细粒度授权」的表象，实际是装饰性的。

对专线的具体影响：`POST /dedicated-line-orders` 只要 `@RequireUser()`，任何 `ownerType='USER'` 的 key 都能下单扣款，不论其 scopes 写了什么。

`ipWhitelist` 是这条路径上唯一真正生效的额外约束（`apikey.strategy.ts:21-23`，非空时强制）。

### P1-5 `OPERATOR` 被静默提升为 `PLATFORM_ADMIN`

`jwt.strategy.ts:34-36` 把 `admin_users.role` 的 `PLATFORM_ADMIN` 与 `OPERATOR` **都**映射为上下文 `PLATFORM_ADMIN`。数据库里的三个角色塌成上下文里的两个。

后果：`RequirePlatformAdmin()` 与 `requireOperatorContext` 都拦不住 `OPERATOR` 账号。整个专线控制面（建节点、改落点策略、导路由、发起迁移、改限额）对运营角色完全开放，而 schema 特意区分了这两个角色说明原意不是这样。

顺带一提，`jwt.strategy.ts` 的命名有误导性：它不是 JWT。实现是**数据库支撑的不透明会话令牌**——SHA-256 摘要 bearer 后查 `sessions` 表（`:14-48`），并显式拒绝 `rt_` 前缀的 refresh token（`:15-17`）。

## 5. 多站隔离缺陷

平台的隔离维度是 `siteId`。绝大多数读写都带 `siteId`（`create-placement-policy.use-case.ts:28-42` 每一个引用校验都带，`delivery-route-import.use-case.ts`、`renew-dedicated-line.use-case.ts`、`dedicated-line-lifecycle.use-case.ts` 亦然）。缺口集中在 **worker 侧的任务领取与投影下发**，因为那条路径的入口是 `jobId` 而不是用户上下文。

| # | 位置 | 查询条件 | 说明 |
|---|---|---|---|
| 1 | `dedicated-line-projection.repository.ts:64` | `{ id: jobId, kind }` | 领取投影任务，无 `siteId` |
| 2 | `dedicated-line-projection.repository.ts:98` | `findUniqueOrThrow({ where: { id: jobId } })` | 领取后回读，无 `siteId` |
| 3 | `dedicated-line-projection.repository.ts:275` | `findUnique({ where: { id: job.id } })` | 完成时回读，无 `siteId` |
| 4 | `dedicated-line-projection.repository.ts:327` | `findUnique({ where: { id: dedicatedLineId } })` | `updateLineReadiness` 汇总就绪度，无 `siteId` |
| 5 | `dedicated-line-order.repository.ts:63` | `updateMany({ where: { id: jobId, kind, status, ... } })` | 领取采购任务，无 `siteId` |

这些**不是当前可利用的越权**：`jobId` 是 UUID，由 worker 从自己的轮询查询里取得，不接受外部输入。真正的问题是隔离不变量没有在数据访问层强制，而是依赖「调用方传进来的 id 一定是自己站点的」这一未被断言的假设。

对比同一文件的 `:160`（`loadClaimedWork`）就带了 `siteId: job.siteId` —— 说明该带 `siteId` 是这个模块的既定意图，上面五处是遗漏而非设计。

`updateLineReadiness`（#4）值得单独提：它按 `dedicatedLineId` 直接跨站读线路并汇总投影状态，写回 `dedicated_lines.status`。这是唯一一处**跨站写**的路径，虽然 id 来自同一事务内的投影记录，但它没有任何断言能证明这一点。

修复方式统一：把 `siteId` 加入这五处的 `where`，并在 `claimRunnableJob` 类型签名上要求调用方显式传入 —— 让编译器而不是评审来保证。

### 维护中间件的站点查询是空过滤器

`maintenance.middleware.ts:32-36`：

```ts
where: { OR: [{ domain: host }, {}] }
```

`{}` 匹配所有行。配上 `orderBy: { createdAt: 'asc' }`，**永远返回最老的站点，与请求的 host 无关**。

多站部署下的实际行为：给最老的站开维护 = 全平台下线；给其他任何站开维护 = 完全没效果。

同一文件还有第二个问题：它在 `AuthGuard` 之前运行，却在 `:26-28` 读 `req.authContext`。此时该字段尚未被填充，所以 `PLATFORM_ADMIN` 绕行维护模式的分支**永不触发**——维护期间管理员也进不来。

### 全局唯一的 email 与幂等键破坏多站模型

`users.email @unique`（`packages/db/prisma/schema.prisma:391`）与 `admin_users.email`（`:434`）是**全局唯一**，不是 `@@unique([siteId, email])`。

这与共享数据库的多站要求（`PRD.md:73-75`）直接矛盾：

- 同一个人无法在两个分站分别注册
- 站 A 的注册接口会通过「邮箱已存在」泄露该人在站 B 有账号

schema 里其他身份都正确按站隔离（`tenants`、`service_skus`、`system_settings` 都是 `@@unique([siteId, ...])`），说明这两处是多站化改造之前的遗留。

`ledger_entries.idempotencyKey @unique`（`:505`）与 `payment_orders.idempotencyKey`（`:520`）同样全局唯一。迁移 `20260612120000_scope_order_idempotency` 已经把 `orders` 改成站内唯一了，但**只改了 orders 就停下**——资金相关的这两张表仍会跨站撞键。

### 租户隔离没有统一执行机制

没有 Prisma middleware、没有 RLS、没有 scoped repository 基类。隔离完全靠 `*.repository.ts` 里约 240 处手写 `where: { siteId, tenantId }`，而 `assertTenantAccess` 只在 **6 个非测试文件的 14 处**被调用。

想补一个客户端级的兜底还有个前置障碍：**124 个文件直接 `import { prisma } from '@ipeasy/db'`**，只有 3 个文件用 `PrismaService`。给 `PrismaService` 加 `$extends` 覆盖不到那 124 个。要引入统一隔离，必须先统一数据访问入口。

## 6. 平台统一契约

### 响应包络

成功（`common/interceptors/envelope.interceptor.ts:20-25`，注册于 `main.ts:31`）：

```json
{ "code": 0, "msg": "success", "data": {}, "requestId": "uuid" }
```

失败（`common/errors/exception-filter.ts:117-131`，注册于 `main.ts:32`）：

```json
{ "code": "NOT_FOUND", "msg": "Not found",
  "data": { "reasonKey": "not_found", "details": {} },
  "requestId": "..." }
```

`details` 缺省时省略（`:214-216`）。契约由 `common/tests/api-contract-integration.spec.ts:38-48` 断言。

注意 `code` 是**多态**的：成功时是数字 `0`，失败时是字符串 `ErrorCode`。前端判断成败不能只看 truthiness。

`AppError(code, reasonKey, httpStatus, message?, details?)` 定义在 `common/errors/app-error.ts:3-13`。ZodError 自动转 422 `VALIDATION_ERROR`（`exception-filter.ts:34-47`）——这是目前唯一的运行时 schema 校验来源，见 [P0-3](#p0-3-缺全局-validationpipe)。

**同一个服务器上并存三种包络方言**，这是读接口时最容易踩的坑：

| 路由前缀 | 行为 |
|---|---|
| 默认 | 上述标准包络 |
| `/res_static/*` | `res-static-compat.ts:31-38`，**无 `requestId`**，错误的 `data` 强制为 `null` |
| `/api/v1/*` | `legacy-api-v1.ts:1-15`，成功时**绕过包络**，错误形状为 `{ statusCode, message, errorCode, timestamp, path }` |

`AUTH_REQUIRED`、`PERMISSION_DENIED`、`TENANT_SCOPE_VIOLATION`、`VALIDATION_ERROR`、`IDEMPOTENCY_CONFLICT`、`WALLET_INSUFFICIENT_BALANCE`、`CURRENCY_NOT_SUPPORTED`、`RESOURCE_MAPPING_MISSING`、`PRICE_MISSING`、`UPSTREAM_DISABLED`、`UPSTREAM_ERROR`、`UPSTREAM_TIMEOUT`、`UPSTREAM_OUT_OF_STOCK`、`UNSUPPORTED_CAPABILITY`、`INTERNAL_ERROR`、`NOT_FOUND`、`DEDICATED_LINE_CONFIG_INVALID`、`CONTROL_NODE_CAPACITY_EXHAUSTED`、`CONTROL_NODE_CONFIG_INVALID`、`PRODUCT_DISABLED`

### 认证上下文

`common/auth/auth-context.ts:6-13`：

```ts
{ ownerId: string; ownerType: OwnerType; siteId: string;
  tenantId: string | null; scopes: string[]; requestId: string }
```

`OwnerType = 'USER' | 'TENANT_ADMIN' | 'PLATFORM_ADMIN' | 'SYSTEM'`（`:4`）。

`common/pagination/pagination.dto.ts`：`PageResult<T> = { page, pageSize, total, items }`（`:12-17`），`DEFAULT_PAGE_SIZE = 20`，`MAX_DISPLAY_PAGE_SIZE = 20`。`normalizePageQuery`（`:22-30`）**静默夹紧**越界值，不报错。

`common/logging/request-id.middleware.ts:10-14` 读 `x-request-id` 或生成 `randomUUID()`，回写响应头，并把请求跑在 AsyncLocalStorage 里（`request-id.context.ts`），供日志与包络取用。

### 契约类型生成链

```
NestJS Swagger（运行时，openapi-setup.ts:5-12，服务 /api/docs + /openapi.json）
  → 提交的 packages/contracts/openapi.json（72KB）
  → scripts/generate.mjs 跑 openapi-typescript
  → packages/contracts/src/generated/api.ts（3862 行）
```

## 7. 需要知道的结构重复

这些不是缺陷，但会让改代码的人改错地方。

## 8. 关于「开一条美国线路」

三台服务器（`185.216.118.241/242/243`）经面板确认均为**香港节点** `HK.CLD.B`，IPv6 `2404:8c80:85:1098::486d` 属 APNIC 亚太注册，同网段、同规格（2C/2GB/20GB/120Mbps）、同批次。

**转发不能让香港 IP 被识别为美国。** IP 归属由 RIR 注册决定，不由转发路径决定。两种可能：香港作为出口——对端看到香港；香港中继到真实美国机器——那台美国机器仍需你拥有。

架构本身已经建模了这件事：`control_nodes.regionCode`。但如 [阶段三](#阶段三选节点与落点策略) 所述，**当前 `regionCode` 从不参与选节点**，地域实际由上游采购参数（`countryCode` / `regionCode` 传给 `buyStaticProxy`）决定。

所以「开一条美国线路」的真实前提有三个，全部未满足：

1. **一台真正位于美国的机器** —— 现有三台是香港
2. **可用的 SSH 或控制台访问** —— **本环境无法触达任何裸 TCP 端口**，原因已定性为本地出网链路上的透明代理，不是服务器故障：对不可能有服务的 65001 端口也「连接成功」、所有端口 0.02 秒接受后一律零字节、`ping` 三台往返 0ms（香港链路物理不可能）。HTTPS 出网正常，故只有裸 TCP/ICMP 被劫持。因此先前的 `banner exchange timeout` / `Connection closed by … port 22` / paramiko banner 错误**全部由该中间设备造成，与 sshd、fail2ban、防火墙、密码无关**，服务器很可能一直正常。服务器侧操作需你在面板 VNC 或 BOOT 面板（`https://boot.yt.net`）执行
3. **专线价格规则** —— 见 [P0-2](#p0-2-生产库五层价格全空专线无法下单)，需产品定价

[P0-1](#p0-1-下单链路字段契约断裂已修复2026-08-23-核实) 已不再是前提 —— 它已修复并核实，下单不会再出现「扣款而不交付」。

可以先做的事：把三台香港机器注册为 `regionCode='HK'` 的控制节点，跑通「下单 → 采购 → 投影下发 → 路由导入 → 线路 ACTIVE」全链路。这不需要改代码，能在拿到美国机器之前验证整条管道。

### 修复顺序

1. **配置专线价格规则**（P0-2）—— 需你定币种、时长档位、单价、起订量。这是现在唯一挡住「下单能跑通」的东西。
2. **API key `scopes` 收口** —— 当前任何 ACTIVE key 权限等于其 ownerType 全量。
3. **`OPERATOR` 与 `PLATFORM_ADMIN` 分离** —— 三个 DB 角色不应塌成两个上下文类型。
4. **维护中间件的 `{}` 空过滤器** —— 多站部署前必修。
5. 补 P0-1 的跨生产者/消费者契约测试，统一两处节点排序器。
6. 五处 `siteId` 与管理控制面守卫层收口。

### 已核实与未核实

已读源码核实：字段契约断裂、`releaseReservation` 判定、四个 handler 的守卫缺口与内层补救、五处 `siteId` 缺失、六个 worker 的注册与开关、迁移的两处 422。

`GET admin/control-plane/lines` 内层已核实：`list-line-limits.use-case.ts:11` 与 `update-dedicated-line-limits.use-case.ts:36` 用同一套 `PLATFORM_ADMIN | TENANT_ADMIN` 判定并按 `tenantId` 收敛，因此 P1-2 覆盖两个路由而非一个。

`stock_reservations` 过期回收已核实**存在且已接线**（此处更正本文早期判断）：

- 实现 `dedicated-line-orders/reclaim-expired-reservations.repository.ts:10`，用例 `domain.ts:199`
- 模块注册 `dedicated-line-orders.module.ts:24,34-36,45`，经 `apps/api/src/worker.ts:17` 导出
- worker 循环 `apps/worker/src/main.ts:98-115`，**没有环境开关，每轮必跑**（注释明确说明「过期预留同时占着库存和客户的钱，系统里没有别的东西会把它们还回来，所以这个扫描不是可选的」）
- 单事务内完成：`releaseReservationTx` 归还库存 → `refundReservationTx` 退款 → 终结任务（`reclaim-expired-reservations.repository.ts:58-60`），`releaseReservationTx` 是 `reservedQuantity` 计数器的唯一所有者，其 ACTIVE 守卫使并发释放或真实交付胜出，不会双重释放或双重退款
- 候选判定保守：只取 `attempt = 0 AND status = QUEUED AND siteId` 一致的预留（`:48`），以此证明上游从未被联系；**缺任务记录的预留永不回收**（`:46-48`）
- 批量大小走 `WORKER_DEDICATED_LINE_RESERVATION_RECLAIM_BATCH_SIZE`（默认 100，`env.schema.ts:50`），间隔 `..._RECLAIM_INTERVAL_MS`（默认 60s，`:49`）

**这改变了 P0-1 的严重程度，但不改变它是阻断项。** 因为 P0-1 的失败发生在 `parseRequest`，此时任务已被 `claimRunnableJob` 抢占（`attempt` 已 ≥ 1）并落入 `NEEDS_OPERATOR`，正好落在回收器刻意排除的范围外。所以：库存与资金**不会自动归还**，仍需人工处理，只是不再是「回收机制根本不存在」，而是「回收机制存在但按设计不覆盖这一类失败」。

回收器的设计是对的 —— 已抢占的任务可能已向上游下单，自动退款会造成真实损失。真正要修的是 P0-1 本身：让订单在被抢占前就带齐字段，这类失败就不会产生。

未核实：生产库的价格配置、`ValidationPipe` 缺失的完整影响面（仅实测了 login/register 四种输入）、三台服务器的实际状态（SSH 在 banner 阶段被阻断）。
